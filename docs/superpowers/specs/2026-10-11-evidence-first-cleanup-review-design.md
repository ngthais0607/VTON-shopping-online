# Evidence-First Repository Cleanup and Code Review Design

## Purpose

Reduce repository clutter and dependency surface, then review and improve code quality and correctness without changing intended product behavior. The work builds on the completed `safe-mvp-remediation` branch so its security, order-lifecycle, and inventory guarantees remain intact.

## Success Criteria

- Generated artifacts that are safe to recreate no longer interfere with normal development commands.
- Tracked source files, assets, and dependencies are removed only when repository-wide evidence shows that they have no consumer.
- The frontend has no ESLint errors or warnings and passes unit tests, TypeScript checking, and a production build.
- The backend unit suite passes, a new empty database upgrades to the Alembic head, and database-backed integration tests run when MariaDB is available.
- Confirmed logic defects are covered by regression tests before their fixes.
- The final report lists deletions, fixes, remaining findings, and any verification that could not run.

## Working Baseline

Work takes place in the `safe-mvp-remediation` worktree and branch, not on `main`. The branch is the source of truth because it already contains the approved security, order, payment, inventory, and frontend remediation work.

The observed baseline is:

- Frontend: 9 tests pass; TypeScript and the production build pass; ESLint reports four warnings.
- Backend: 59 tests pass and four database integration tests are skipped when MariaDB is unavailable.
- A stale `pytest-cache-files-*` directory can prevent default pytest collection.
- The repository contains many zero-consumer UI modules and placeholder assets, but string-reference counts alone contain false positives and are not sufficient evidence for deletion.

## Cleanup Classification

Every cleanup candidate belongs to one of four classes:

1. **Regenerable artifact**: caches, build output, logs, and test databases that are ignored and recreated by standard commands.
2. **Unused tracked artifact**: source or static assets with no source, test, configuration, convention-based, or runtime consumer.
3. **Unused dependency**: a package with no direct or indirect consumer after unused source removal.
4. **Unproven candidate**: anything whose use cannot be disproved confidently; it remains in place and is reported if noteworthy.

The cleanup must not remove active development environments (`backend/.venv`, `frontend/node_modules`), the active `.worktrees` directory, operational examples, migrations, runtime templates, or documentation required to understand the current branch.

## Evidence Rules

Frontend source analysis must account for alias imports, relative imports, re-exports, tests, configuration, CSS references, public-asset paths, and Next.js file conventions. Backend analysis must account for Python imports, FastAPI router registration, Alembic discovery, ARQ worker/job entry points, templates, tests, and string-based runtime references.

A source file or asset may be deleted only when all relevant checks show no consumer. A dependency may be removed only after its consuming source is settled and its possible build-time, peer, transitive, and configuration use has been checked. Lockfile updates must be generated by the package manager.

Deletion proceeds in small, independently verifiable groups so a regression can be attributed to a specific group.

## Documentation Cleanup

Documentation cleanup is intentional, not based only on Git ignore status:

- Remove all historical intermediate artifacts under `.superpowers/sdd/`.
- Remove Superpowers plans and specs dated before 2026-10-10.
- Keep the current `safe-mvp-remediation` design, amendment, implementation plan, and errata because they explain the branch used as the cleanup baseline.
- Remove the obsolete remediation draft explicitly superseded by the errata.
- Keep this cleanup design and its implementation plan while the work is active.

## Code Review Strategy

### Backend

Review in descending risk order:

1. Authentication and authorization boundaries.
2. Order lifecycle, payment behavior, and inventory invariants.
3. Transaction, commit, rollback, and concurrency behavior.
4. Worker, queue, and email failure handling.
5. Remaining CRUD, validation, and serialization paths.

The review focuses on correctness, broad or swallowed exceptions, duplicated business rules, unclear responsibility boundaries, and code whose structure makes an invariant difficult to verify. File length alone does not justify a refactor. Public API behavior remains unchanged unless the existing behavior is demonstrably unsafe or incorrect.

### Frontend

Review the user flows in this order:

1. Authentication and role-aware navigation.
2. Catalog, product selection, wishlist, and cart.
3. Checkout and payment presentation.
4. Account and order tracking.
5. Administrative dashboard and CRUD screens.

The review focuses on hook dependencies, stale state and request races, loading and error states, type safety, duplicated domain mappings, and uncontrolled side effects. Visual redesign and unrelated UX expansion are outside scope.

## Finding and Fix Policy

Findings are classified as Critical, High, Medium, or Low.

- Critical and High findings within the reviewed flows are fixed and receive regression coverage.
- Medium findings are fixed when the change is local, low-risk, and verifiable within the approved gates.
- Low findings that are primarily stylistic are recorded rather than used to expand the project into a broad refactor.

Any confirmed behavior defect receives a failing regression test before production code is changed. Cleanup-only deletions use existing compile, lint, test, and build gates as their safety net.

## Verification Sequence

After each deletion or fix group, run the narrowest relevant checks. Before completion, run the full sequence:

1. Frontend unit tests.
2. ESLint with zero warnings.
3. `tsc --noEmit`.
4. Next.js production build.
5. Backend unit tests using normal collection after stale artifacts are removed.
6. Alembic upgrade from an empty database to head.
7. MariaDB integration tests when the configured service is available; otherwise report them as not run, not passed.
8. A final dead-reference and dependency scan.
9. `git diff --check` and a clean review of the complete diff.

## Error Handling and Rollback

If removing a candidate breaks a gate, restore that candidate unless the failure proves a small, in-scope missing reference that should be corrected. If a review uncovers a defect whose safe correction requires an API redesign, schema migration beyond the current remediation, or a large architectural refactor, stop and raise it as a follow-up instead of silently expanding scope.

## Deliverables

- A reduced set of tracked UI modules, assets, and dependencies backed by evidence.
- Removal of approved generated and historical Superpowers artifacts.
- Focused clean-code and correctness fixes with regression coverage.
- Updated package metadata and lockfile where dependencies are removed.
- A final review report with severity, file references, validation results, skipped external checks, and remaining risks.

## Out of Scope

- New product features or visual redesign.
- Broad router/service/repository restructuring based only on file size.
- Changes to public API contracts without a confirmed correctness or security defect.
- Deleting active virtual environments, installed Node packages, active worktrees, migrations, runtime templates, or the current remediation documentation.
- Claiming MariaDB concurrency coverage passed when the service was unavailable.
